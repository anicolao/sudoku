# E2E testing guide

This guide defines the browser-level contract for Sudoku. Playwright scenarios
are the primary proof of user-visible behaviour; pure Sudoku rules and replay
invariants remain the responsibility of unit/property tests.

The approach combines the strongest patterns in `../games/jaipur`, `../food`,
and `../dosage`: vertical user journeys through the real UI, one step primitive
for assertions/screenshots/docs, an exact game-log oracle, deterministic browser
inputs, local-storage recovery, same-origin privacy enforcement, and a separate
service-worker-enabled offline project.

## 1. Non-negotiable principles

### A scenario is a tracer bullet

Each scenario starts with a real browser action, crosses Svelte commands, the
event repository, validation, deterministic replay, selectors, and rendering,
then ends in a visible result. Do not test UI against a hand-built component
state or bypass the repository to make a screenshot convenient.

Storage fixtures are allowed only to establish a state that earlier scenarios
have already proven through the UI. Fixtures contain canonical events, use the
same public storage schema, and are replayed by normal application startup.

### Semantic and visual proof are paired

Every documented checkpoint must first assert meaning, then layout safety, then
capture a screenshot. A screenshot never substitutes for accessible names,
event contents, board values, timer status, or game-log text.

### Zero means zero

`maxDiffPixels: 0` lives in `playwright.config.ts`. Helpers and individual tests
must not override it, add masks, relax thresholds, or blur dynamic areas.
Dynamic inputs are controlled instead: fixed clock, fixtures, IDs, locale,
timezone, fonts, viewport, reduced motion, and software rendering.

The only supported browser/platform combination is Playwright Chromium on
macOS. CI uses the pinned GitHub-hosted `macos-15` runner rather than
`macos-latest`, so an image-label change cannot silently replace the screenshot
environment. GitHub lists `macos-15` as a standard hosted-runner label in its
[runner reference](https://docs.github.com/en/actions/reference/runners/github-hosted-runners).
Baseline filenames include `macos`; zero tolerance applies to this single
reviewed baseline set.

### Wait for evidence, never time

`waitForTimeout`, sleeps, interval polling, and arbitrary animation delays are
forbidden. Wait on an observable state such as a role becoming visible, an
event count changing, `data-app-ready="true"`, service-worker cache readiness,
or a storage value satisfying an assertion.

### Generated docs have one writer

Per-scenario `README.md` files are generated by the same step calls that perform
assertions and screenshots. They are written only when
`UPDATE_E2E_DOCS=1`, only by the canonical `phone` project, and with one worker.
The dedicated offline scenario is the only exception: its sole `offline`
project writes its own walkthrough. Normal test runs never modify the worktree.

IDs, and no shared storage. The offline project is serial.

## 4. Deterministic fixtures

Every scenario fixes:

- a generator seed, selected chapter level, generator version, and exact
  expected puzzle;
- event IDs and game IDs through an injected E2E ID source;
- browser clock with `page.clock.install()`;
- locale, timezone, viewport, reduced motion, and device scale;
- preferences such as mistake checking and automatic note cleanup;
- all storage contents, normally an empty store;
- the app build/version marker.

Production code receives dependencies through module construction, not ambient
`Math.random()`/`Date.now()` calls. E2E injection is enabled only by a build-time
test flag and changes sources of IDs/time, not domain behaviour.

The canonical sample puzzle is produced by the real generator from a fixed seed.
Its givens, solution, uniqueness, and allowed logical solve trace are checked by
unit tests. E2E specs inject the seed at the normal generation boundary and
assert the generated stable ID rather than bypassing generation with a board.

Each test begins with a new browser context and therefore an empty IndexedDB
database and `localStorage` namespace before optionally installing a fixture.
Never depend on execution order. Storage-specific tests exercise IndexedDB;
the E2E build may expose a read-only flat event mirror and a bounded fixture
replacement hook, neither of which is read by application code.

## 5. Unified step pattern

`TestStepHelper.step()` binds verification, layout checks, screenshot naming,
and documentation into one operation:

```ts
await steps.step('note-added', {
  description: 'A pencil note is visible in the selected cell and game log',
  verifications: [
    {
      spec: 'Row 4 column 7 contains note 3',
      check: async () => {
        await expect(cell(page, 4, 7)).toHaveAttribute('aria-label', /notes 3/);
      }
    },
    {
      spec: 'The canonical stream appended one note event',
      check: async () => {
        await expectEventTypes(page, ['game/started', 'cell/note-toggled']);
      }
    }
  ]
});
```

The helper must:

1. run every semantic verification and retain its human-readable `spec`;
2. assert `data-app-ready="true"` and `data-persistence-status="local"` (or the
   explicitly requested state such as `memory-only`);
3. await local fonts and images and verify no unfinished CSS transitions;
4. move the pointer outside meaningful UI and hide the caret;
5. prove the document is at scroll position zero, the document needs no
   horizontal or vertical scrolling, every visible element remains inside the
   viewport without clipped overflow, and every visible non-board target is at
   least 44×44 CSS px;
6. call `expect(page).toHaveScreenshot(filename)` with no tolerance override;
7. record description, relative image path, and checks for documentation.

Screenshot filenames are generated, never hand-written:

```text
000-note-added-phone-macos.png
001-value-entered-phone-macos.png
```

The helper's `generateDocs()` writes this shape:

```md
# Values and notes

The player records candidates and commits a value through the real event store.

## A pencil note is visible in the selected cell and game log

![A pencil note is visible...](./screenshots/000-note-added-phone-macos.png)

**Verifications:**

- [x] Row 4 column 7 contains note 3
- [x] The canonical stream appended one note event
```

Call `generateDocs()` from `test.afterEach` only after a successful scenario so
a failed partial run cannot overwrite a reviewed walkthrough.

## 6. Layout assertions

Layout checks are executable requirements applied before every documented
screenshot.

- The page must remain at `scrollX = 0` and `scrollY = 0`.
- The scrolling element must fit the viewport in both axes, with only a one CSS
  pixel rounding allowance.
- Every visible element must remain within the viewport.
- Any element whose overflow clips or scrolls must have
  `scrollWidth <= clientWidth + 1` and `scrollHeight <= clientHeight + 1`.
- Unbounded collections use fixed-size pagination or a compact latest-item
  projection; nested scrolling regions are not allowed.
- Every visible non-board interactive target is at least 44×44 CSS px.
- The same rules apply at 200% zoom and in landscape; compact layouts may remove
  secondary chrome, but they keep the board and required actions available.

The helper returns precise element labels, rectangles, and scroll dimensions on
failure.

## 7. Event-stream and game-log oracles

### Canonical stream oracle

`expectEventStream(page, expected)` reads `sudoku.event-store.v1`, validates it
with the production storage schema, and compares stable fields. It ignores no
domain field. Timestamps and IDs are exact because they are injected.

Each user action asserts:

- exactly one expected event was appended, or zero for a rejected/cancelled
  action;
- sequences remain contiguous and IDs unique;
- reload produces the same event document;
- the visible board and history agree with replay.

The complete-game scenario stores its expected event list in a sibling
`expected-event-stream.ts`, mirroring Jaipur's full game-log oracle. This makes
missing, extra, or reordered actions reviewable.

### Visible game-log oracle

`GameLogOracle` advances one expected entry after each meaningful action. For
every page/viewport under test it asserts:

- canonical log count and the compact newest visible entry;
- newest entry's `data-event-type`;
- exact formatted text;
- expanded accessible text for compact cell notation;
- completion consumed the entire expected list.

The event stream and visible log are intentionally separate assertions: the
stream proves source facts, while the log proves their human-readable
projection.

## 9. Representative scenario details

### Values and notes

Use a fixed puzzle and perform:

1. select r4c7;
2. enter Notes mode and add 2, 3, and 8;
3. remove 2;
4. switch to Number and enter the correct value;
5. enter a conflicting value elsewhere with checking off;
6. undo, redo, erase, then reload.

At every checkpoint assert the cell accessible label, visual state, canonical
event, log entry, number count, and replay after reload. Unit tests, not this one
browser path, exhaust all 81 cells and digits.

### Complete puzzle

Start from a canonical fixture whose event stream leaves a representative set
of cells empty. Fill the remainder through keyboard/UI actions. Assert after
each move with the stream/log oracle, then prove:

- all 81 projected values match the known solution;
- completion is derived without a redundant `game/completed` event;
- input controls are read-only;
- elapsed time, mistakes, hints, and move count are exact;
- History reconstructs the same summary after reload;
- no action after completion appends an event.

### Storage recovery

Test separate fresh contexts for:

- IndexedDB open/write failure before first write: play works in memory and
  persistence language changes;
- malformed outer JSON: affected raw text is quarantined and no partial board is
  shown;
- a bad event inside valid JSON: only that game is incompatible;
- a supported old storage fixture: migration is atomic and replay-equivalent;
- an unknown future version: original bytes remain unchanged and other valid
  streams still open.

Never “fix” corruption in the fixture from the test. Exercise the production
recovery path.

## 10. Privacy enforcement

Before app code runs, install instrumentation that records or throws on:

- `window.fetch`;
- `XMLHttpRequest.open`;
- `WebSocket`;
- `EventSource`;
- `navigator.sendBeacon`.

Also listen to every Playwright `request`. In ordinary operation, every browser
request must be a same-origin `GET` for the document, a bundled static asset, or
the cache-busted static revision manifest.
Any other method, origin, analytics endpoint, remote font, source map request,
or dynamic content request fails the scenario.

Run the check across start, input, hint, completion, history, settings, reload,
storage error, and clear-all flows. Assert the only local keys are documented
`sudoku.*` keys. Service workers are blocked in this suite to avoid conflating
cache traffic with application traffic.

## 11. Installed offline scenario

Offline proof uses the production build and `serviceWorkers: 'allow'`:

1. launch a fresh context online against loopback preview;
2. load the app and wait for explicit `data-offline-ready="true"` after the
   service worker is active and the versioned shell cache is complete;
3. prove the client fetched uncached `version.json` without adding a visible URL
   parameter, and that the manifest itself is absent from Cache Storage;
4. start a puzzle, enter a value, pause, and close the page;
5. set the context offline and reopen the installed URL;
6. assert exact replay, resume, complete the puzzle, and open History;
7. reload offline again and prove the completed board and History remain;
8. inspect Cache Storage to ensure it contains application assets but not the
   `sudoku.event-store.v1` contents;
9. return the test context online during cleanup.

This scenario is serial, has a documented project-level timeout if production
browser restart needs more than the shared limit, and still uses observable
conditions rather than sleeps.

## 12. Accessibility checks

Automated checks include axe with documented exclusions only for confirmed tool
false positives. Semantic assertions additionally verify:

- one labelled grid with exactly 81 gridcells;
- roving `tabindex` and arrow/Home/End movement;
- fixed/editable, value, note, selection, conflict, and mistake state in cell
  accessible names/properties;
- visible focus and no keyboard trap;
- Number/Notes pressed state and number-button remaining counts;
- polite live announcements that occur once per action;
- correct focus entry/return for hint confirmation and log sheets;
- pause removes board values from visual and accessibility exposure;
- forced-colour selection/conflict indicators remain distinguishable;
- 200% zoom reflows without horizontal document scrolling.

Automated results supplement, not replace, the manual VoiceOver and NVDA checks
listed in [UX_DESIGN.md](UX_DESIGN.md).

## 13. Commands and review workflow

Proposed scripts:

```sh
npm run check
npm run test:unit
npm run test:e2e
npm run test:e2e -- tests/e2e/003-values-notes-conflicts
npm run test:e2e:update-snapshots
npm run test:e2e:offline
npm run build
npm run verify:change
```

`test:e2e:update-snapshots` runs in the pinned canonical screenshot environment,
sets `UPDATE_E2E_DOCS=1`, forces one worker for the docs-writing project, and
surfaces every changed generated doc and image for review. Ordinary tests never
call an update command.

Review every visual diff beside its semantic assertion changes. A legitimate
visual change updates the implementation, expectations, screenshot, generated
walkthrough, and relevant UX requirement in one reviewable commit. Refactors
with no observable change must keep screenshots byte-identical.

The repository verifier must reject:

- focused or skipped tests;
- retries above zero;
- `waitForTimeout` or other arbitrary sleeps;
- screenshot masks or nonzero tolerances;
- per-test timeout overrides outside the declared offline project;
- manually edited generated walkthroughs;
- unreferenced screenshots;
- unexpected worktree changes after a normal test run.

## 14. MVP browser exit criteria

- Every required scenario passes with zero retries.
- Semantic assertions and Chromium/macOS screenshots pass with zero differing
  pixels on the pinned `macos-15` runner.
- Each canonical scenario README is regenerated and reviewed from the same
  successful steps.
- The event-stream and game-log oracles consume their complete expectations.
- No ordinary runtime request violates the local-only policy.
- The production build completes restart, play, completion, and history offline.
- Phone, narrow phone, landscape, tablet, desktop, zoom, reduced motion,
  keyboard, touch, and automated accessibility evidence is retained.
- Running the full verifier twice produces no new files or changed state.
